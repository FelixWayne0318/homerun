# Homerun 使用教程（小白版）

> 适用对象：第一次接触本项目、没有量化交易经验、但需要把系统跑起来并安全使用的人。
> 适用环境：本机 macOS，项目目录 `/Users/ahs/Projects/homerun`，前端 `http://127.0.0.1:3000`，后端 `http://127.0.0.1:8000`。
> 重要原则：**先沙盒、后实盘；先小额、后放大。** 本文所有实操都只涉及沙盒/影子模式，不涉及真实资金。

**开始前请先记住三条：**

1. **回测不要用 `Auto` 当默认数据源。** 要选 `Datasets`，并勾选带 `PARQUET` 的数据集；否则可能一直 0%、看起来像卡死。
2. **沙盒是即时成交，不是挂单撮合。** 下单后直接成为持仓，没有“挂单→撤单”这个动作。
3. **实盘当前不可用。** 缺少 Polymarket 私钥/凭证，看到 `initialized=false` 是正常降级，不是可以点的功能。
4. **顶部 `工作器 10/11 · 1 警告` 不是故障。** API 的 11 个 worker 都在 running；前端按“启用”统计，`news` 是设计内关闭（`enabled=false`），因此显示为 1 个 amber。判断故障要看 API 和 `last_error`，不要只看这个数字。

## 1. 这个系统是做什么的

一句话：**Homerun 是一个预测市场（Polymarket、Kalshi）的自动扫描 + 策略计算 + 模拟/实盘交易系统。**

它每 30～60 秒做一轮事情：

1. 从 Polymarket 等平台拉取市场、订单簿、价格；
2. 用 30 个策略计算有没有“定价错误”或“套利机会”；
3. 把机会写进数据库，显示在“机会”页面；
4. 交易员（Bot）按配置决定要不要下单；
5. 下单先走影子模式或沙盒账户，不碰真钱；
6. 你在界面上看机会、持仓、盈亏，决定是否上线实盘。

### 1.1 它能做的事

- 自动扫描几千个预测市场；
- 计算 YES+NO 套利、跨市场价差、结算滞后、天气/新闻/加密等策略；
- 用沙盒账户模拟买卖、结算、算盈亏；
- 用历史快照做回测；
- 在影子模式下验证交易员逻辑，不花真钱。

### 1.2 它现在不能做、或不能按旧方式做的事（2026-11-10 实况）

| 事项 | 现在的真实情况 |
| --- | --- |
| 实盘下单 | 不能。没有 Polymarket 私钥，`GET /api/trader-orchestrator/live/status` 返回 `initialized=false`、`credentials_configured=false`。 |
| 回测默认窗口 | `Auto` 模式只发滚动 `start/end`，会落到 live ingestor universe 去读全量历史 parquet，可能一直 0%。**正确做法是 `Datasets` 选择明确数据集**，不是“只能跑 10 分钟”。 |
| 从机会卡片直接买沙盒账户 | 卡片上通常没有这个按钮。沙盒下单用第 7 节的 `execute` API；交易员手动买入走另一条链路。 |
| 沙盒撤单 | 不支持。沙盒是即时成交模型，没有挂单，也就没有可撤的单。 |
| 新闻 | 操作者已主动停用新闻主开关，暂不支付 LLM 费用。`news` 进程现在会随 `news` 平面启动，但 `enabled=false` 时只空转，不发起新闻扫描。 |
| 天气 | 已于 2026-11-10 实际恢复：`weather` worker 在跑；最近一次实测 `last_scan=2026-11-10T08:37:43Z`，每轮 200 个市场、102 个意图、54 条策略机会，机会总数 156。实际时间以你查询 `weather-workflow/status` 时为准。 |

## 2. 小白必须先懂的 12 个词

| 词 | 大白话解释 |
| --- | --- |
| 市场（Market） | 一个可以下注的问题，比如“某地会不会下雨”。 |
| YES / NO | 同一个问题的两个方向。YES 价格 0.6，表示市场认为有 60% 概率发生。 |
| 机会（Opportunity） | 系统算出来“价格不合理、可能有利润”的一组下注。 |
| 策略（Strategy） | 一套判断规则，负责发现机会。系统内置 30 个。 |
| 扫描器（Scanner） | 定时把所有市场拉一遍、喂给策略的程序。 |
| 交易员 / 机器人（Trader / Bot） | 真正决定“这个策略信号要不要下单、下多少”的执行单元。 |
| 影子模式（Shadow） | 只记账、不真下单。用来验证交易员逻辑。 |
| 沙盒账户（Sandbox） | 用虚拟资金模拟买卖的账户，和真钱完全隔离。 |
| 实盘（Live） | 真钱、真下单。需要私钥、授权、风控。 |
| 敞口（Exposure） | 当前押了多少钱在市场里。 |
| ROI | 回报率，利润 ÷ 成本。 |
| 回测（Backtest） | 用历史数据重放一遍，看策略过去会不会赚钱。 |
| 数据集（Dataset） | 回测/Data Lab 里已经导入或录制好的一段历史数据；带 `PARQUET` 的才是回测可直接用的。 |

补充两个运维词：

- **worker**：后台常驻任务，比如扫描器、发现、对账、兑付。
- **plane**：一组 worker 的进程分组，例如 `trading`、`detection`、`news`。

## 3. 启动系统并确认它真的在运行

### 3.1 四种启动/重启方式

**方式 A：双击启动（最简单）**

在 Finder 里打开：

```
/Users/ahs/Projects/homerun/scripts/launchers/Homerun.command
```

双击它会自动检查并拉起后端、前端、数据库。

> **如果桌面窗口报 `ModuleNotFoundError: No module named '_tkinter'`**：这只影响 tkinter 桌面壳，不影响 Web 服务。当前 `run.sh` 会自动寻找带 tkinter 的 Python；找不到时直接打开 `http://127.0.0.1:3000`，不会再让启动器崩掉。想恢复桌面窗口，可在普通 Terminal 执行 `brew install python-tk@3.11`（会连带升级 `python@3.11`，沙箱内可能报 `EPERM`，需要你本人在 Terminal 里装）。

> **启动器不会再杀掉 launchd 托管的进程。** 早期 `cleanup_stale_homerun_processes` 会把 `workers.host`、`uvicorn`、`gui.py` 一视同仁地 `kill -9`，所以双击启动器会看到“Cleaned up 6 stale ...”，launchd 随后又把它们拉起来，造成 `tracked_traders` 短暂 stale。现在清理前会先读 `launchctl list`，跳过所有 `com.homerun.*` 正在托管的 PID；只有真正没有 launchd 托管的旧进程才会被清掉。

**方式 B：已经在常驻运行**

这台机器已经用 launchd 托管了 **11 个已加载服务**，通常不需要手动启动。开机后会自动起来。

```bash
cd /Users/ahs/Projects/homerun
launchctl list | grep homerun
```

当前正常会看到这 11 条（PID 会变，不用记）：

```
com.homerun.backend
com.homerun.frontend
com.homerun.postgres
com.homerun.redis
com.homerun.worker-detection
com.homerun.worker-discovery
com.homerun.worker-trading
com.homerun.worker-jobs
com.homerun.worker-news
com.homerun.logrotate
com.homerun.dbbackup
```

`com.homerun.worker-news` 就是承载 `news + weather` 的平面。2026-11-10 恢复天气前它是未加载状态，`launchctl list` 里只有 10 条；本次按 9.4 节执行 `bootstrap` 后，它已加载并运行，所以现在是 11 条。不要把它和“新闻主开关”混为一谈：进程加载不等于新闻会调用 LLM。

如果少了一个服务，补启动（以 backend 为例）：

```bash
launchctl bootstrap "gui/$(id -u)" ~/Library/LaunchAgents/com.homerun.backend.plist
```

> 不要把 `501` 写死。不同机器的用户 UID 可能不同，统一用 `gui/$(id -u)`。

**方式 C：手动启动后端（仅在已经 bootout 掉 launchd 服务时）**

```bash
cd /Users/ahs/Projects/homerun/backend
KMP_DUPLICATE_LIB_OK=TRUE nohup ./venv/bin/uvicorn main:app \
  --host 127.0.0.1 --port 8000 >> ../data/backend_out.log 2>&1 &
```

后端启动约 40 秒可用。`KMP_DUPLICATE_LIB_OK=TRUE` 不能省，否则 macOS 上可能因为 OpenMP 重复加载直接退出。

> **方式 C 只在你已经 `bootout` 掉 `com.homerun.backend` 时使用。** 如果 launchd 已经在托管后端，再手动起一个 uvicorn 会争抢 `8000` 端口，表现为“新进程启动失败、旧进程又被 launchd 拉起”，很容易误判。日常改代码后的正确重启是下面的方式 D。

**方式 D：launchd 托管下的正确重启（最常用）**

```bash
# 后端 API 改完：重启后端
launchctl kickstart -k "gui/$(id -u)/com.homerun.backend"

# 扫描器 / 事件 / SLO：重启 detection 平面
launchctl kickstart -k "gui/$(id -u)/com.homerun.worker-detection"

# 发现 / 已追踪钱包：重启 discovery 平面
launchctl kickstart -k "gui/$(id -u)/com.homerun.worker-discovery"

# 交易编排 / 对账 / 兑付：重启 trading 平面
launchctl kickstart -k "gui/$(id -u)/com.homerun.worker-trading"

# 新闻 + 天气：重启 news 平面
launchctl kickstart -k "gui/$(id -u)/com.homerun.worker-news"
```

重启后不要只看 `launchctl list` 的 PID，按这个顺序确认：

```bash
# 1. 后端是否真的 ready
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/health/ready

# 2. 对应平面的日志有没有 “Worker plane lock acquired” / “Worker plane started”
tail -n 30 /Users/ahs/Projects/homerun/data/worker_detection_out.log
```

> **不要用 `kill <PID>` 重启 launchd 托管的后端。** 常见结果是 PID 变了但服务没真正重启，或者被 launchd 立即拉起，日志看起来“像重启了”。统一用 `kickstart -k`。

### 3.2 健康检查分三级，不要只看一个 `/health`

| 级别 | 命令 | 正常值 | 说明 |
| --- | --- | --- | --- |
| 存活 | `GET /health` | `200`，`{"status":"ok"}` | 只证明进程还在、HTTP 能应答。 |
| 就绪 | `GET /health/ready` | `200`，`status:"ready"` | 证明 scanner / database / ws_feeds / polymarket_api / redis 五项依赖都就绪。 |
| 后台任务 | `GET /api/workers/status` | 当前 11 个中 11 个 `running`；`news` 的 `enabled=false` | 看每个 worker 的真实心跳和 `stale` 标记。 |

实跑：

```bash
curl -s -o /tmp/health.json -w '%{http_code} %{time_total}s\n' \
  http://127.0.0.1:8000/health
cat /tmp/health.json

curl -s -o /tmp/ready.json -w '%{http_code} %{time_total}s\n' \
  http://127.0.0.1:8000/health/ready
python3 -m json.tool /tmp/ready.json

curl -s http://127.0.0.1:8000/api/workers/status | python3 -c \
'import json,sys
d=json.load(sys.stdin)["workers"]
print("total",len(d),"running",sum(1 for w in d if w.get("running")))
for w in d:
    print(w["worker_name"], "running=", w.get("running"), "stale=", w.get("stale"))'
```

2026-11-10 最后一轮复测结果：

- `/health`：`200`，约 `0.008s`；
- `/health/ready`：`200`，约 `0.4s`，五项检查全 `true`；
- `/api/workers/status`：共 **11** 个 worker，**11 个 `running=true`**，`last_error` 全空；
- 顶部状态条：**`工作器 10/11 · 1 警告`**。这里的 10 是 10 个启用中的绿色 worker，1 个 amber 是设计内关闭的 `news`（`enabled=false`，显示 `PAUSED`）；不是 worker 崩了。

恢复前后的对照：

| 时点 | API worker | 顶部 | 说明 |
| --- | --- | --- | --- |
| 恢复前 | 11 个中 9 个 running | `9/11 · 2 警告` | `news` 进程未加载；`weather` 心跳 stale。 |
| 恢复后 | 11 个中 11 个 running | `10/11 · 1 警告` | `news + weather` 平面已加载；`news` 仍 `enabled=false`，循环空转，不调 LLM；`weather` 已完成新一轮。 |

恢复后两个关键 worker 的真实状态：

| worker | 状态 | 说明 |
| --- | --- | --- |
| `news` | `running:true`，`enabled:false` | 进程在跑，但主开关关闭；`last_scan` 停留在 2026-11-09T10:37:02Z，`pending_intents=0`，没有发起新扫描。 |
| `weather` | `running:true`，`stale` 消失 | 最近一次实测 `last_scan=2026-11-10T08:37:43Z`。每轮 200 个市场 / 102 个意图 / 54 条策略机会 / 156 条机会；首轮 135.19 秒，run-once 第二轮 176.3 秒。 |

所以这台机器现在的正常基线是：**API `11/11 running`，顶部 `10/11 green + 1 amber`（amber 就是 `news` 设计内关闭）**。不要为了把数字凑成 `11/11` 去打开新闻主开关；那会重新产生 LLM 费用。

> 注意：`/api/health` 这个带 `api` 前缀的路径确实不存在，会返回 404；项目的健康路由是顶层 `/health`。不要把两者混用。

### 3.3 打开界面

浏览器访问：

```
http://127.0.0.1:3000
```

第一次打开如果页面空白，等 5～10 秒；后端要加载市场缓存。数据页“地图”首屏空白 3～4 秒也属正常，等地图瓦片加载完即可。

地图页 2026-11-10 曾出现 3 条 `422`，根因是 `instability` 接口收到 `limit=250` 但上限只允许 200；已把上限改为 500。现在打开“数据 → 地图”，控制台应为 **0 error / 0 warning**。如果仍看到 422，先强制刷新（`Cmd+Shift+R`），再确认后端已用 `kickstart` 重启。

### 3.4 顶部状态条怎么读

顶部不是“装饰”，它是快速体检：

| 字段 | 含义 |
| --- | --- |
| `工作器 10/11 · 1 警告` | 前端按“启用”统计：10 个绿色 + 1 个 amber（`news` 设计内关闭）。API 实际上是 11 个全 `running`。 |
| `市场 39-40` | 当前扫描到的市场数量，会随扫描轮次变化；不是固定值。 |
| `交易员 12` | 交易员/机器人数量，可能随启停变化。 |
| `新闻 12` / `天气 54` | 对应模块的机会/意图数量；天气 54 是实际跑出的策略机会数，新闻关闭时这个数字可能来自历史。 |
| `信号 P:60` | 当前扫描器产出的信号数；P 是 primary，后面的 `S/X/F` 是其他来源。 |
| `策略 30` | 已加载策略数量。 |
| `漏斗 96.8K→0 0.0%` | 扫描量到机会的漏斗；0% 不一定异常，要看机会页是否有数据。 |
| `事件 1分 186` | 最近 1 分钟的事件摄取计数，用于判断数据源是否还在动。 |
| `挂单 2` | 实盘编排器的挂单口径；沙盒持仓不计入。 |

## 4. 界面地图：10 个标签分别干什么

| 标签 | 作用 | 新手要不要马上用 |

**Cortex 在哪里？** 在 `机器人` 页顶部右侧的 `Cortex` 按钮，点开是抽屉，里面有三个页签：`活动 / 记忆 / 设置`。详见第 9.2 节。

### 4.1 设置页常用分组

设置页里可以改的内容，按新手使用顺序：

| 分组 | 作用 | 新手建议 |
| --- | --- | --- |
| 语言 / 外观 | 界面语言、浅色/深色/跟随系统 | 先改成简体中文和深色，减少误读 |
| 搜索 | Polymarket 平台开关、每页结果数量 | 默认即可；数量越大越吃内存 |
| 扫描器 | 扫描间隔、机会阈值、池容量 | 不要为了“更快”把间隔调到 5 秒，会触发限流 |
| 通知 | Telegram 提醒 | 可选，不配也能用 |
| 界面锁定 | 本地屏幕锁、闲置超时 | 单人本机可不配 |
| 交易 VPN/代理 | 交易请求走代理 | 只影响交易链路，不影响浏览器刷新 |
| 网络访问 | 允许局域网设备访问面板 | 默认仅本机；开之前先确认网络环境 |
| 发现 | 钱包发现的增长与维护 | 默认即可，改大后更耗 RPC/内存 |
| 数据提供商 | Polybacktest API Key、逆向工程默认值 | 回测要导入数据集时才需要 |
| 数据库 | 清理与维护 | 不要随手点清理，先看提示 |
| 导入 / 导出 | 迁移交易配置包 | 改配置前先导出备份 |
| 区块链 RPC | 钱包监控的 Polygon RPC | 公共层级有速率限制，长期跑建议填自己的 RPC |

> 设置页的分组展开本身不会保存；每个分组里要单独点“保存/应用”。上线前不要把“能展开”当成“已配置”。

## 5. 第一次上手：30 分钟走完一遍

### 第 1 步：确认账户

打开“账户”标签，看顶部账户选择器：

- 如果显示“未选择账户”，点开下拉，选择一个沙盒账户；
- 如果没有沙盒账户，点“沙盒交易台”，再点“新建沙盒账户”。

### 第 2 步：创建一个沙盒账户

路径：**账户 → 沙盒交易台 → 左侧 `新建`**（空账户时按钮文案是 `新建沙盒账户`）。

填写：

## 7. 沙盒账户完整实操

> 这一节是“真按步骤做一遍”的版本。全部是虚拟资金，不会动真钱。
> 当前沙盒是**即时成交**模型：下单即持仓，不产生挂单，所以没有撤单。

### 7.1 先查账户和余额

```bash
curl -s http://127.0.0.1:8000/api/simulation/accounts | python3 -m json.tool
```

记下你的账户 `id`，例如：

```
fe35cca1-dd76-49e1-b1d2-2f816f65e9cf
```

也可以直接用 API 创建账户（字段限制与界面一致）：

```bash
curl -s -X POST http://127.0.0.1:8000/api/simulation/accounts \
  -H 'Content-Type: application/json' \
  -d '{"name":"沙盒测试2","initial_capital":10000,"max_position_pct":10,"max_positions":10}' \
  | python3 -m json.tool
```

`initial_capital` 必须 ≥ 100 且 ≤ 10,000,000；`max_position_pct` 必须 1–100；`max_positions` 必须 1–100 的整数。

### 7.2 找一条可下单的机会

```bash
curl -s "http://127.0.0.1:8000/api/opportunities?limit=1" | python3 -m json.tool | head -40
```

记下 `id` 和 `positions_to_take` 里的 `token_id`、`outcome`、`price`。

### 7.3 下单（买 10 份）

把下面的 `ACCOUNT_ID` 和 `OPPORTUNITY_ID` 换成你自己的：

```bash
ACCOUNT_ID="fe35cca1-dd76-49e1-b1d2-2f816f65e9cf"
OPPORTUNITY_ID="把机会 id 填这里"

curl -s -X POST "http://127.0.0.1:8000/api/simulation/accounts/$ACCOUNT_ID/execute" \
  -H 'Content-Type: application/json' \
  -d "{\"opportunity_id\":\"$OPPORTUNITY_ID\",\"position_size\":10}" | python3 -m json.tool
```

请求体只认两个关键字段：

```json
{"opportunity_id":"...","position_size":10}
```

- `position_size` 可省略；省略时按账户单仓上限自动算；
- 如果传 `position_size`，必须 **≥ 1.0**，传 `0.5` 会返回 `422`；
- 机会不存在会返回 `404`，提示 `Opportunity not found`。

返回里重点看：

- `trade_id`：这笔成交的编号；
- `status`：一般是 `OPEN`（不是 `executed`）；
- `total_cost`：扣了多少钱；
- `expected_profit`：预期利润。

### 7.4 看持仓

```bash
curl -s "http://127.0.0.1:8000/api/simulation/accounts/$ACCOUNT_ID/positions" | python3 -m json.tool
```

### 7.5 结算（模拟开奖）

```bash
TRADE_ID="上一步返回的 trade_id"

curl -s -X POST \
  "http://127.0.0.1:8000/api/simulation/trades/$TRADE_ID/resolve?winning_outcome=NO" \
  | python3 -m json.tool
```

**`winning_outcome` 是 Query 参数，不是 JSON body。** 只能填 `YES` 或 `NO`，写在 URL 的问号后面。

返回：

- `resolved_win` 或 `resolved_loss`；
- `actual_payout`：赔付；
- `actual_pnl`：这笔盈亏。

结算后回“账户/沙盒交易台”刷新，应该看到余额和盈亏变化。

### 7.6 这个流程里没有“撤单”

模拟账本是**即时成交**模型：

- 没有挂单，所以没有可撤的单；
- 下单后直接变成持仓；
- 想“反悔”只能结算或删除账户重建。

实盘侧倒是有撤单接口：

```
DELETE /api/trader-orchestrator/live/orders/{order_id}
DELETE /api/trader-orchestrator/live/orders
```

但当前没有实盘凭证，暂时用不上。不要拿这两条去验证沙盒撤单，沙盒永远不会产生挂单。

## 8. 回测怎么用（含避坑）

### 8.1 界面入口

路径：**策略 → 研究 → 回测工作室 → 左侧 Setup / PICK DATA**

界面有三档数据源：

- `Auto / ROLLING WINDOW`：按当前时间往前推 N 天；
- `Recording session / CAPTURED WINDOW`：已录制的窗口；
- `Datasets / MULTI-SELECT VENDOR DATA`：导入的数据集。

### 8.2 关键避坑：不要用 `Auto` 当默认

**现象：** 点了运行，状态一直 `Worker claimed run`，进度 0%，`snapshots_processed` 一直是 0，看起来像卡死。

**根因不是“窗口太长”这么简单：**

- `Auto` 只发滚动 `start/end`，没有明确的数据集范围；
- 后端会落到 live ingestor universe，去读全量历史 parquet 事件流；
- 在 `parquet_backend._read_file_rows` 的 `json.decoder.raw_decode` 上反复空转；
- 所以进度恒 0、快照数恒 0，取消也未必立刻生效。

**正确做法：在 `DATA SOURCE` 里选 `Datasets`，勾选一个带 `PARQUET` 的数据集。**

已真实点通的一条：

1. `DATA SOURCE` 选 `Datasets`；
2. 勾选 `BTC Up/Down · 5m · 2026-11-08 03:05 UTC (settled UP)`（约 `4,164 snaps`、`2 tokens`）；
3. 点 `Continue to Run`；
4. 点 `运行回测`；
5. 结果应为 `completed`（或 `ok`）、`2.0s` 左右、`4146` 快照。

对应的数据集 ID 是：

```
polybacktest:f662df0204314654
```

窗口：

```
2026-11-08T03:06:13Z → 2026-11-08T03:09:59Z
```

这不是“只能用 10 分钟”的意思，而是**这条数据集本身就是 4164 个快照的明确范围**。选更大的数据集也可以，但要观察内存和耗时，不要回到 `Auto` 全量扫描。

### 8.3 用 API 跑一个明确的回测（推荐复制这段）

```bash
cd /Users/ahs/Projects/homerun

SLUG=basic
DATASET_ID=polybacktest:f662df0204314654
START=2026-11-08T03:06:13Z
END=2026-11-08T03:09:59Z

data/Postgres.app/Contents/Versions/16/bin/psql \
  "postgresql://homerun:homerun@127.0.0.1:5432/homerun" -t -A \
  -c "select source_code from strategies where slug='$SLUG';" > /tmp/bt_src.py

python3 - "$SLUG" "$DATASET_ID" "$START" "$END" <<'PY'
import json, sys, time, urllib.request
slug, dataset_id, start, end = sys.argv[1:5]
payload = {
    "source_code": open('/tmp/bt_src.py').read(), "slug": slug,
    "provider_dataset_ids": [dataset_id],
    "start": start, "end": end,
    "initial_capital_usd": 1000.0,
    "seed": 42,
}
req = urllib.request.Request(
    "http://127.0.0.1:8000/api/backtest/runs/enqueue",
    data=json.dumps(payload).encode(),
    headers={"Content-Type": "application/json"},
)
rid = json.load(urllib.request.urlopen(req))["run_id"]
print("run_id:", rid)
for _ in range(40):
    time.sleep(1)
    st = json.load(urllib.request.urlopen(f"http://127.0.0.1:8000/api/backtest/runs/{rid}/status"))
    print(st["status"], "|", st["message"], "| snaps=", st.get("snapshots_processed"))
    # 成功既可能写 completed，也可能写 ok；两者都是终态。
    if st["status"] in ("completed", "ok", "failed", "cancelled"):
        break
d = json.load(urllib.request.urlopen(f"http://127.0.0.1:8000/api/backtest/runs/{rid}"))
e = d.get("execution") or {}
print("trades =", e.get("trade_count"), "snapshots =", e.get("n_snapshots"), "return% =", e.get("total_return_pct"))
PY
```

关键点：

- **必须传 `provider_dataset_ids`。** 只传 `start/end` 是旧写法；现在 `enqueue` 会在入队时把 `session_id` / `provider_dataset_ids` 解析成 `token_ids + start/end`，解析不到会返回 **404**，并提示 `Import them via Data Lab → Providers first`。
- 成功终态可能是 `completed`，也可能是 `ok`（当前队列 worker 对成功任务会写 `ok`）。轮询脚本必须同时接受这两个值，否则会一直等。
- 不要用 `/api/backtest/run`（同步接口，已弃用）。用 `/runs/enqueue` + `/runs/{id}/status`。

### 8.4 怎么看结果

| 结果 | 含义 |
| --- | --- |
| `completed` / `ok` + `snapshots > 0` | 回测正常 |
| `completed` / `ok` + `trades = 0` | 正常，策略在该数据集没触发；**不等于故障** |
| `snapshots = 0` | 真的没读到数据，检查数据集是否选对 |
| 长时间 `queued` | worker 没领到任务，或标签页在后台；见 8.5 |
| 长时间 `running` 且 0% | 回到了 Auto/全量扫描，或数据量超出内存包线；取消并改用 Datasets |

### 8.5 如果界面长时间停在 `Queued`

已知前端 `BacktestStudio` 的后台轮询曾因标签页失焦停住。当前已加 `refetchIntervalInBackground: true`，正常不会再长期停在 `Queued`。

如果仍遇到：**刷新页面即可自愈**。待运行的 run id 存在 localStorage 的 `hr_backtest_pending_run_id`，重载后会自动落地并清除，不会生成重复任务。

### 8.6 导出 PDF 报告（当前受本机依赖限制）

路由存在：

```
GET /api/backtest/runs/{run_id}/report.pdf
```

但本机当前缺少 `libpango`，实测返回 **503**，响应是 JSON 错误而不是 PDF。要用它，先安装 WeasyPrint 依赖：

```bash
brew install pango cairo libffi gdk-pixbuf
```

然后重启后端再试。未安装前，把它当作“未启用的可选功能”，不要因为 PDF 503 就判断回测失败；回测结果本身看 `/runs/{id}` 的 `execution`。

### 9.4 恢复天气（不产生 LLM 费用）

天气和新闻共用一个 `news` 进程。要让天气恢复，按顺序执行。**本节已于 2026-11-10 实际执行并跑完一轮**，不是纸面流程。

**第 0 步：清掉残留的新闻扫描请求（防止启动后意外扫新闻）**

先看新闻控制表里有没有残留请求：

```bash
curl -s http://127.0.0.1:8000/api/news-workflow/status \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); print(d.get("enabled"), d.get("requested_scan_at"), d.get("pending_intents"))'
```

如果输出第三项不是 `None`，执行一次“全暂停 → 全恢复”把它清掉：

```bash
curl -s -X POST http://127.0.0.1:8000/api/workers/pause-all  | python3 -m json.tool
curl -s -X POST http://127.0.0.1:8000/api/workers/resume-all | python3 -m json.tool
```

`pause-all` 会调用 `clear_news_scan_request` 和 `clear_weather_scan_request`；清完后 `requested_scan_at` 应为 `None`。本次实测残留值是 `2026-11-09T16:14:29Z`，就是靠这一步清掉的。**不要跳过这一步直接启动 plane**：`news` 即使 `enabled=false`，残留请求仍可能触发一次扫描并产生 LLM 费用。

**第 1 步：关掉新闻主开关**

```bash
curl -s -X POST "http://127.0.0.1:8000/api/workers/news/enable?enabled=false" \
  | python3 -m json.tool
```

**不要用这个 POST 响应里的 `worker.enabled` 判断。** 本次实测：接口返回 `200`，但响应体里的 `worker.enabled` 仍是 `true`（读到了旧快照）；真正生效要查：

```bash
curl -s http://127.0.0.1:8000/api/news-workflow/status \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); print(d.get("enabled"), d.get("requested_scan_at"))'
```

见到 `False None` 才算关闭成功。

**第 2 步：打开天气主开关**

```bash
curl -s -X POST "http://127.0.0.1:8000/api/workers/weather/enable?enabled=true" \
  | python3 -m json.tool
```

**第 3 步：启动 news 平面（天气跟着它一起跑）**

先检查它是否已经注册：

本次实测：执行 `bootstrap` 前 `launchctl print` 返回 `113`（`Could not find service ... in domain for user gui: 501`）；`bootstrap` 返回 `0`，随后 `launchctl print` 返回 `0`，`launchctl list` 出现 `com.homerun.worker-news`（PID 5850）。它同时拉起 `news` 和 `weather` 两个 worker。

**第 4 步：确认“真的在跑”，不要只看一次 `/api/workers/status`**

```bash
curl -s http://127.0.0.1:8000/api/weather-workflow/status | python3 -m json.tool
curl -s http://127.0.0.1:8000/api/news-workflow/status  | python3 -m json.tool
```

判断标准：

- `weather-workflow/status` 的 `running` 为 `true`，`last_scan` 在最近更新；
- `news-workflow/status` 的 `running` 为 `true`，`enabled` 为 `false`；
- 两者 `requested_scan_at` 都为 `null`。

**重要实测坑**：`/api/workers/status` 有 5 秒缓存，bootstrap 后约 12 秒内它可能仍显示 `weather running=false stale=true`，这是旧缓存回吐，不代表启动失败。本次等到缓存刷新后，`/api/workers/status` 才变成 `weather running=true`、`news running=true`、共 **11/11 running**。判断天气是否恢复，以 `weather-workflow/status` 的 `last_scan` 和 `worker_snapshot` 为准，不要用一次 `/api/workers/status` 下结论。

**第 5 步：触发一轮真实扫描并核对结果**

```bash
sleep 180
curl -s http://127.0.0.1:8000/api/weather-workflow/status \

```

> 一轮天气扫描实测约 **2～3 分钟**（首轮 135.19 秒、run-once 第二轮 176.3 秒）。不要 `sleep 10` 就判断失败；看 `current_activity` 是否变成 `Weather strategy cycle complete...`。

本次实际结果：

- 最新 `last_scan`：`2026-11-10T08:37:43Z`；恢复后已跑过多轮，较早的首轮是 `2026-11-10T03:36:59Z`；
- `current_activity`：`Weather strategy cycle complete: 54 opportunities from 102 intents.`；
- 每轮结果一致：市场 `200`、合约/意图 `102`、策略机会 `54`、机会总数 `156`；

- `pending_intents=163` 是历史待处理意图计数，不等于本轮产出；
- `signals_emitted_last_run=0`，`intents_created=0`，本轮是报告/机会生成，没有自动下单。

**实际恢复后的状态**

| 项 | 实测值 |
| --- | --- |
| `/api/workers/status` | 11 个 worker，**11 个 running** |
| 顶部状态条 | **`工作器 10/11 · 1 警告`**；amber 来自设计内关闭的 `news`，不是 worker 崩溃 |
| `weather` | `running:true`、`enabled:true`、`stale:None` |

**这里要纠正教程旧版的一个错误结论**：旧版写“恢复天气后应变成 `11/11 · 健康`”，这是把 **API 的 running 计数**和**前端按启用状态的计数**混用了。实际现在 API 是 11/11 running，但前端顶部显示 **`10/11 · 1 警告`**：10 个启用中的 worker 是绿色，`news` 因为 `enabled=false` 显示 PAUSED/amber。`enabled=false` 表示“不干活”，不等于“进程没跑”；这 1 个 amber 是设计内的省钱状态，不是故障。

## 10. 风控与紧急停止

### 10.1 先认识三类开关

| 开关 | 作用 | 是否跨重启保持 | 怎么用 |
| --- | --- | --- | --- |
| `pause` / `start` | 临时暂停/恢复某个 worker（`is_paused`） | 否；`resume-all` 会恢复 | `POST /api/workers/{worker}/pause`、`/start` |
| `enable?enabled=` | 子系统主开关（`is_enabled`） | **是**，跨重启保持，必须显式再打开 | `POST /api/workers/{worker}/enable?enabled=false` |
| Kill Switch | 阻止某个交易员开新仓 | 由交易员配置决定 | `POST /api/traders/{trader_id}/block-new-orders` |

**不要把 `pause-all` 当成永久停用。** `pause-all` 只改临时暂停位，`resume-all` 会全部恢复；要长期关掉某个子系统，用 `enable?enabled=false`。

### 10.2 全局暂停/恢复

```bash
curl -s -X POST http://127.0.0.1:8000/api/workers/pause-all | python3 -m json.tool
curl -s -X POST http://127.0.0.1:8000/api/workers/resume-all | python3 -m json.tool
```

全局暂停期间，单独 `start` 会被拒绝并返回 **409**：

```json
{"detail":"Global pause is active. Use /workers/resume-all first."}
```

这时应先 `resume-all`，再单独操作。

### 10.3 交易员级 Kill Switch / 手动控制

先设置交易员 ID：

```bash
TRADER_ID="把交易员 id 填这里"
```

```bash
# 阻止某个交易员开新仓（enabled=true 表示打开阻断）
curl -s -X POST "http://127.0.0.1:8000/api/traders/$TRADER_ID/block-new-orders" \
  -H 'Content-Type: application/json' \
  -d '{"enabled":true,"requested_by":"operator","reason":"manual risk stop"}'

# 停止 / 启动 / 只跑一轮
curl -s -X POST "http://127.0.0.1:8000/api/traders/$TRADER_ID/stop"
curl -s -X POST "http://127.0.0.1:8000/api/traders/$TRADER_ID/start"
curl -s -X POST "http://127.0.0.1:8000/api/traders/$TRADER_ID/run-once"

# 手动买入（影子/实盘按交易员模式走）
# 这个接口必须有 positions 和 size_usd，不能空 body 直接 POST。
curl -s -X POST "http://127.0.0.1:8000/api/traders/$TRADER_ID/manual-buy" \
  -H 'Content-Type: application/json' \
  -d '{"size_usd":10,"positions":[{"token_id":"把 token_id 填这里","price":0.55,"side":"BUY"}]}'
```

实盘撤单（当前无凭证，不可用）：

```
DELETE /api/trader-orchestrator/live/orders/{order_id}
DELETE /api/trader-orchestrator/live/orders
```

### 10.4 新手建议

- 始终让交易员处于 `shadow`；
- 单笔金额不超过 $10；
- 不要打开 `live` 模式，除非私钥、授权、风控都配好；
- 每天看一次“业绩”和“持仓”，确认没有异常单；

## 11. 常见故障与处理

| 现象 | 可能原因 | 怎么处理 |
| --- | --- | --- |
| 页面打不开 | 前端进程没起 | `launchctl list | grep homerun`，补 `com.homerun.frontend` |
| `/health` 不是 200 | 后端进程挂了 | `launchctl kickstart -k "gui/$(id -u)/com.homerun.backend"` |
| `/api/health` 404 | 路径写错 | 正确路径是顶层 `/health`；`/api/health` 不存在 |
| 机会一直是 0 | 扫描器首轮未完成/加载态 | 等 60 秒刷新；仍为 0 查 worker 状态 |
| 机会子标签显示 0，但总数不是 0 | REST 还没返回 | 等页面加载完，不是故障 |
| 顶部显示 `10/11 · 1 警告` | 正常基线：`news` 设计内关闭，amber 是 PAUSED | 看 `/api/workers/status` 是否 11/11 running、`last_error` 是否为空；不是故障，不要为凑 11/11 打开新闻 |
| 顶部显示 `9/11 · 2 警告`（仅恢复前） | news 平面未加载 + weather stale | 这是 2026-11-10 恢复前的状态；按 9.4 恢复后 API 11/11 running、顶部 10/11 green + 1 amber |
| 地图页 3 条 `422` | 前端 `limit=250`，旧后端上限 200 | 已修复；若仍出现，强制刷新并确认后端已 `kickstart -k` 重启 |
| 地图首屏空白 3～4 秒 | 地图瓦片/信号接口仍在加载 | 等瓦片加载；控制台应为 0 error，若持续空白看 422 行 |
| 天气不更新 | news 平面没运行，天气跟着停 | 见 9.4“恢复天气” |
| 天气 API `running:true` 但 worker stale | 控制开关和实际心跳不是一回事；`/api/workers/status` 还有 5 秒缓存 | 以 `weather-workflow/status` 的 `last_scan` 和 DB/`worker_snapshot` 为准，等缓存刷新再复核 |
| 重启某个平面后该 worker 仍显示 stale | 启动快照可能还没写成，或 `/api/workers/status` 在读 5 秒缓存 | 等 1 个 interval 再看；若持续 `running=false` 且 `last_error` 为空，重启对应平面并检查日志有没有 `Worker plane started` / `started; first ... pending.` |
| `tracked_traders` 在长周期里显示 stale | 全量 sweep 可能跑 2～4 分钟，旧快照只在周期结束时写一次 | 已修复：worker 每 30 秒只刷新一次 heartbeat 时间，不改活动/统计；若仍 stale，看日志里有没有 `Tracked-traders worker started` 和 `heartbeat failed` |
| 双击 `Homerun.command` 报 `_tkinter` | 桌面 GUI 依赖 tkinter，Homebrew Python 没装 | 不影响 Web；`run.sh` 会回退到带 tkinter 的 Python 或直接打开浏览器；要桌面窗口就装 `python-tk@3.11` |
| 持仓 5 条但敞口 $0.00 | 沙盒持仓不计入实盘敞口 | 口径差异，不是错 |
| 回测卡在 claimed / 0% | Auto 全量扫描，或数据量超内存 | 取消任务，改用 `Datasets`，不要用 Auto |
| 回测一直 Queued | 后台标签页轮询停住 | 刷新页面；`hr_backtest_pending_run_id` 会自动落地 |
| 回测 `ok` 不是 `completed` | 成功任务当前会写 `ok` | 两者都当成功，不要只等 `completed` |
| 回测 trades=0 | 策略在该数据集没触发 | 正常，不是故障；看 `snapshots` 是否 >0 |
| 回测 404 数据集 | 数据集未导入/ID 写错 | 先到 Data Lab → 提供者导入；提示会写 `Import them via Data Lab → Providers first` |
| PDF 导出 503 | 本机缺 `libpango` | 安装 `pango/cairo/libffi/gdk-pixbuf` 后重启；未装就是不可用 |
| Cortex 显示“已启用”但 API `enabled:false` | UI/API 口径差异 | 以 API 为准；当前 Cortex 未启用 |
| Cortex 活动里有 `initialize_ai()` 报错 | 2026-11-07 的历史 activity | 不是每次打开都报；以最新活动时间为准 |
| 实盘按钮报未初始化 | 缺私钥/凭证 | 正常降级，不要反复点 |
| 日志大量 ERROR | 数据库重启/外键冲突 | 先看当前是否复现，历史错误不代表现在有问题 |

## 14. 常见问题 FAQ

**Q1：为什么机会卡片上没有“买入”按钮？**
卡片视图通常没有；切到“列表”或“终端”。买入走交易员的手动买入接口，不是直接买沙盒账户。

**Q2：为什么我买了之后沙盒账户余额没变？**
因为你用的是交易员的影子下单，账记在交易员订单里，不进沙盒账户。要动沙盒账户，用第 7 节的 `execute` 接口。

**Q3：为什么持仓有 5 条，顶部敞口是 $0.00？**
顶部敞口取实盘编排器口径，沙盒持仓不计入。不是数据错误。

**Q4：为什么回测一直不动？**
先看你选的数据源。`Auto` 会落到全量历史 parquet，可能一直 0%；改用 `Datasets` 并勾选明确数据集。不要只把窗口改短，窗口短但仍是 Auto 也可能空转。

**Q5：为什么回测成功了却显示 `ok`，不是 `completed`？**
当前成功任务可能写 `ok`，两者都是终态。教程里的轮询同时接受 `completed`、`ok`、`failed`、`cancelled`。

**Q6：为什么新闻是停的？**
操作者要求暂不支付 LLM 费用，主动把新闻主开关设为 `false`。`news` 进程本身可以随 plane 运行（`running:true`），只是空转、不扫描；这不影响天气。

**Q7：为什么天气 `running:true` 但数据不更新？**
先看 `weather-workflow/status` 的 `last_scan` 和 `pending_intents`，再看 `/api/workers/status` 的 `stale`。`running` 是控制/心跳字段，不等于刚刚跑过；`/api/workers/status` 还有 5 秒缓存。2026-11-10 实测 `weather` 已恢复：最近 `last_scan=2026-11-10T08:37:43Z`，每轮 54 条策略机会。若 `last_scan` 长期不动，按 9.4 检查 plane 是否还在。

**Q8：能不能直接做实盘？**
当前不能。缺 Polymarket 私钥，实盘服务 `initialized=false`。配置完整凭证后还要先做最小金额验证。

**Q9：数据会不会丢？**
数据库有每日备份、日志轮转；但沙盒账户是测试账本，不建议存重要数据。

**Q10：Cortex 到底启用了没有？**
当前 `GET /api/cortex/status` 返回 `enabled:false`。如果抽屉 UI 显示“已启用”，以 API 为准；这是已知的口径差异。
