## 二、三处恒为 0 的根因（核心）

### 1. 顶栏「新闻 0」——三条链同时出问题
- **成本常量错**：`workflow_orchestrator.py` 把单次 LLM 成本硬编码为 `$0.02`，而实测 `deepseek-chat` 为 `$0.00358/次`（`llm_usage_log` 194 次调用、均 25172 输入 token）。$0.25 的周期预算因此只放行 **12 次**（模拟复现：`OLD_0.02 → 12/20`，`MEASURED → 20/20`）。
- **调用被上游吃光**：12 次全给事件抽取，rerank / edge 全部走 fallback，`model_probability` 回填市价 ⇒ `edge_percent=0` ⇒ `actionable=false` ⇒ 计数恒 0。DB 实证：88 条 finding，`edge_percent>0` 为 **0**，拒绝原因 60 条中 47 条是 `llm_budget_exhausted`。
- **前端停止轮询**：5 处计数查询写的是 `refetchInterval: isConnected ? false : 30000` —— WebSocket 一连上就再也不轮询，只能等推送。某数据源没推 ⇒ 数字永久冻结（天气曾长期停在 23，而后端实际 0）。

**已改并提交（a5fd72d4）**：
- 成本改为模型感知：实测 `by_model` 均值 → `PRICING` 按 1500/500 token 估 → 兜底 0.02；并打印 `News cycle LLM budget: ...` 便于核对。
- 5 处计数查询改 `isConnected ? 60000 : 30000`，WS 优先、兜底轮询。
- 天气面板 4 处、新闻面板 4 处同样加 60s 兜底（提交 f59773f1）。
- **状态：前端已生效**（顶栏天气从 0 变 20 即为证据）；**后端成本修复需重启 plane 生效**（见第四节）。

### 2. 顶栏「天气 0」——重启写空快照
- `workers/weather_worker.py` 启动时用 `opportunities=[]` 覆盖 `weather_snapshot`，而下一轮扫描间隔是 **4 小时**（`scan_interval_seconds=14400`）。每次重启面板就清零并冻结 4 小时。

- **已验证**：手动 `POST /weather-workflow/run` 后快照恢复，`/weather-workflow/opportunity-ids` 现返回 **total=20**，顶栏天气已从 0 变 20（前端兜底轮询也一并生效）。

## 补充：新闻链路第二轮修复（2026-11-09 00:20–00:50）

1. **语义索引超时**：18928 个市场全量编码，上限仅 30s → 每轮超时 → 静默降级「continuing without ML」→ 0 候选。改为 120s/240s，并在市场集合未变时复用索引。

**根因**：底图瓦片地址被硬编码为 `a/b/c.basemaps.cartocdn.com`，本机代理把该域名解析到 fake-ip `198.18.205.186` 且无出口路由，瓦片全部超时；同时 `map.on('error')` 把所有瓦片错误当成「地图初始化失败」，弹出红条并遮住情报图层。

- `90fe7cc6`：瓦片源抽成 `VITE_MAP_TILE_URL` / `VITE_MAP_TILE_URL_LIGHT` 覆盖变量，缺省仍走 CARTO 三源；深色主题下对覆盖源压暗（`raster-brightness-max 0.58` 等）维持情报层对比。

**实测**：`tile.openstreetmap.org/2/1/1.png` → 200 / 6725 B；浏览器截图确认欧洲/非洲/中东真实底图 + 黄色/绿色情报点 + 国界 GeoJSON 正常叠加，署名已为 OpenStreetMap。`npx tsc --noEmit`：13 条基线（全在 `TradingPanel.tsx`）/ `WorldMap.tsx` 0 条。

### 2. 新闻 `orchestrator_min_edge` 假开关（已修复，阈值已生效）

**根因**：`run_cycle` 把 `min_edge` / `min_conf` / `orchestrator_min_edge` 写死成 `0.0` 传给 `edge_estimator.estimate_batch` 与 `intent_generator.generate`，Settings 里的 5% / 0.45 / 10% 从未生效。

**修复**：新增 `_float_setting()`，三处改为读 `wf_settings`（`min_edge_percent` 5.0、`min_confidence` 0.45、`orchestrator_min_edge` 10.0）。

**运行态验证**：重启前每轮 `26/50/42/23 findings` 且 edge 低至 1.5% 仍标 actionable；重启后同样规模产出但 `actionable` 归零 —— 36 findings 全部被 5% / 0.45 拦下，证明阈值真正生效。

### 3. 索引每轮全量重建（已修复）

**根因**：复用判断为「市场数量与上次完全相等」。市场池每轮都有几只进出（18872 → 18856 → 18845），条件永远不成立 → 每轮重编码 ~19k 文档，耗时约 60–175 s，吃掉整个周期预算，edge 阶段被 `llm_budget_exhausted` 全部拒绝。

**修复**：改为「数量变化 > 10%，或距上次重建 ≥ 15 分钟」才重建，并记录 `_indexed_built_at`。

**实测**：冷启动轮 181 s（含一次重建），次轮 94.9 s 且日志无 `index rebuilt`；此后周期稳定在 94–156 s。

### 4. 周期预算 90 s → 180 s（已修复）

worker 是「跑完再等 `scan_interval_seconds`(120 s)」，不是固定间隔，所以放宽单轮上限不会造成周期重叠。90 s 放不下 rerank + edge，导致 edge 阶段只跑到 2–5 次调用就被截断。改为 180 s。

### 5. `cycle_llm_call_cap` 30 → 60（设置层调整）

cap=30 时 event 分 9、rerank 分 6、edge 只剩 15，而每轮有 20 个 cluster —— 连「每个 cluster 估 1 条」的保底都凑不齐（15 < 20），与 `max_edge_evals_per_article=6` 明显不匹配。经 `PUT /api/news-workflow/settings` 调到 60，回读确认写入。

### 6. 事件总线丢审计事件（已修复）

`parquet_backend._write_parquet_batch` 用 `json.dumps(payload)` 且无 `default`，payload 含 `datetime` 时抛 `TypeError`，整批丢弃，每轮固定报 `parquet flush failed for news.update/workflow_cycle/... (1 events lost)`。补充 `_payload_json_default`（datetime → ISO、bytes → utf-8、set → list），实测 datetime 可正常序列化；重启后该报错消失（最后一条停在 01:38）。

### 7. 新闻「信息流」面板全空（已修复）

**根因**：`news/feed/articles` 读的是 API 进程内存里的 `news_feed_service` 缓存，只在启动时 `load_from_db()` 填充一次。清空动作或 API 进程重启后，内存为 0，而 worker 仍在往 `news_article_cache` 写文章（表内 2051 行、最新 14 分钟前），于是面板永远显示「信息流中没有文章」。

**修复**：`GET /news/feed/articles` 在 `article_count == 0` 时先从 DB 重载再返回。

**实测**：接口由 `total:0` 变为 `total:1000`（内存上限 1000 条），面板显示「新闻（1000）」并列出 Reuters / CNBC 等真实条目。

### 8. 结论：新闻 actionable 仍为 0 的原因（非缺陷，待决策）

链路已完整跑通：每轮 `200 articles → 20 clusters → 56–68 findings`，其中约 5 条被真正估值，edge 峰值 5.0%、confidence 峰值 0.81，**但从未在同一条上同时达到 `edge ≥ 5%` 且 `confidence ≥ 0.45`**，因此 0 actionable、0 intent。

两个结构性原因：
1. **召回太窄**：20 个 cluster 里只有约 5 个能走到 edge 阶段（其余被 `low_news_relevance`、rerank 阈值、时间对齐过滤），预算投不下去。
2. **阈值与模型能力不匹配**：`orchestrator_min_edge=10%` 意味着模型必须认为市价比真实概率错 10 个百分点，而 prompt 明确要求「市场通常有效、偏离需强证据」。这组阈值等价于「几乎永不出手」。

这不是代码 bug，是产品参数取向。要产出机会有两条路，需拍板：
- **降阈值**（如 `min_edge_percent` 5→2、`min_confidence` 0.45→0.30、`orchestrator_min_edge` 10→3）：立刻有产出，但会引入低质量机会。
- **提召回**（改 embedding 模型 / 相似度权重 / rerank 阈值）：从源头增加有效候选，属设计改造，工作量较大。

在拿到决定前，保持设计本意（宁缺勿滥），不擅自放宽。

**用户决定（2026-11-09）：按第一方案放宽** —— `min_edge_percent` 5.0 → 3.0、`min_confidence` 0.45 → 0.35、`orchestrator_min_edge` 10.0 → 3.0。

**执行与验证**（PUT `/api/news-workflow/settings` 落库并重启 news plane）：
- 库内回读：`news_workflow_min_edge_percent=3.0`、`news_workflow_min_confidence=0.35`、`news_workflow_orchestrator_min_edge=3.0`、`cycle_llm_call_cap=60`。
- `cycle #2: 200 articles -> 20 clusters -> 75 findings (1 actionable) -> 1 intents`。
- 放行条目：「Will China's CPI increase by at least 1.3% over the 12 months?」，edge 4.95% / confidence 0.40，同时满足 3.0 / 0.35。
- 同轮其它已估值条目均被正确拦下：`2.50/0.32`（conf 不足）、`1.70/0.35`（edge 不足）、`0.80/0.54`、`0.25/0.63`、`0.05/0.54`（edge 不足）—— 说明两道闸门按新值精确工作，不是「放水」。

**注意**：产出是条件性的，只在出现 `edge ≥ 3% 且 confidence ≥ 0.35` 的条目时才有机会，不是每轮必有。若希望更稳定的密度，下一步应提高召回（20 个 cluster 里通常只有 5–6 个能走到估值阶段）。
