## 二、三处恒为 0 的根因（核心）

- 成本改为模型感知：实测 `by_model` 均值 → `PRICING` 按 1500/500 token 估 → 兜底 0.02；并打印 `News cycle LLM budget: ...` 便于核对。

### 4. 周期预算 90 s → 180 s（已修复）

worker 是「跑完再等 `scan_interval_seconds`(120 s)」，不是固定间隔，所以放宽单轮上限不会造成周期重叠。90 s 放不下 rerank + edge，导致 edge 阶段只跑到 2–5 次调用就被截断。改为 180 s。

### 7. 新闻「信息流」面板全空（已修复）

**实测**：接口由 `total:0` 变为 `total:1000`（内存上限 1000 条），面板显示「新闻（1000）」并列出 Reuters / CNBC 等真实条目。

### 8. 结论：新闻 actionable 仍为 0 的原因（非缺陷，待决策）

链路已完整跑通：每轮 `200 articles → 20 clusters → 56–68 findings`，其中约 5 条被真正估值，edge 峰值 5.0%、confidence 峰值 0.81，**但从未在同一条上同时达到 `edge ≥ 5%` 且 `confidence ≥ 0.45`**，因此 0 actionable、0 intent。

两个结构性原因：
1. **召回太窄**：20 个 cluster 里只有约 5 个能走到 edge 阶段（其余被 `low_news_relevance`、rerank 阈值、时间对齐过滤），预算投不下去。
2. **阈值与模型能力不匹配**：`orchestrator_min_edge=10%` 意味着模型必须认为市价比真实概率错 10 个百分点，而 prompt 明确要求「市场通常有效、偏离需强证据」。这组阈值等价于「几乎永不出手」。

这不是代码 bug，是产品参数取向。要产出机会有两条路，需拍板：
- **降阈值**（如 `min_edge_percent` 5→2、`min_confidence` 0.45→0.30、`orchestrator_min_edge` 10→3）：立刻有产出，但会引入低质量机会。
- **提召回**（改 embedding 模型 / 相似度权重 / rerank 阈值）：从源头增加有效候选，属设计改造，工作量较大。

在拿到决定前，保持设计本意（宁缺勿滥），不擅自放宽。

**用户决定（2026-11-09）：按第一方案放宽** —— `min_edge_percent` 5.0 → 3.0、`min_confidence` 0.45 → 0.35、`orchestrator_min_edge` 10.0 → 3.0。

**执行与验证**（PUT `/api/news-workflow/settings` 落库并重启 news plane）：
- 库内回读：`news_workflow_min_edge_percent=3.0`、`news_workflow_min_confidence=0.35`、`news_workflow_orchestrator_min_edge=3.0`、`cycle_llm_call_cap=60`。

## 补充：天气机会概率全为 100% 的根因与修复（2026-11-09 11:00–13:30）

### 1. 现象

34 条天气机会全部 `model_probability = 1.0`，ROI 从 +148% 到 +195900%。同一城市同一天出现自相矛盾的记录：米兰「最低温正好 0°C」与「最低温 -2°C 或以下」同时 100%，「正好 1°C / 2°C / 3°C / 5°C」也各自 100% —— 这在逻辑上不可能。

### 2. 逐层排除（全部实测，不是推断）

| 层 | 结论 | 证据 |
|---|---|---|
| `parse_weather_contract` | 正确 | `lowest … be 24°C` → `between 23.5/24.5, temp_min_range`；`highest … be 13°C` → `12.5/13.5`；`… or higher` → `gt 20.0`；`below 32°F` → `lt 0.0` |
| `_temp_range_probability` | 正确 | `SCALE=2.0`；`(15.8, 23.5, 24.5) = 0.008094` |
| `OpenMeteoWeatherAdapter.forecast_probability` | 正确 | 米兰 0°C 实跑：`source_probabilities={'gfs_seamless': 0.0077, 'icon_seamless': 0.0199}` |
| `workflow_orchestrator` 传参 | 正确 | `operator / threshold_c / threshold_c_low / threshold_c_high` 全部从 `ParsedWeatherContract` 透传给 adapter 与 `build_weather_signal` |

单点三段都正确，说明断裂发生在「策略层」。

### 3. 根因

`backend/services/strategies/weather_distribution.py` 的跨桶归一化：

```python
all_buckets = [current_bucket] + sibling_markets
raw_probs = [各桶原始概率]
total_prob = sum(raw_probs)
if total_prob > 0:
    normalized_probs = [p / total_prob for p in raw_probs]   # ← 旧逻辑
```

每个温度问句在库里是**独立的 event**，`sibling_markets` 为空 → `all_buckets` 只有 1 个桶 → `p / p = 1.0`。**单桶事件必然被归一化成 100%**，于是模型概率恒为 1.0，`edge = (1 - 0.0005) * 100 ≈ 99.95%`，ROI 被放大到荒谬数量级。

归一化的本意（注释 "full cross-bucket normalization"）是「同一事件有完整温度桶集合时，把概率在桶间分配」；单桶没有可分配的空间，绝不能放大。

### 4. 修复

只在**确实持有完整桶集**时归一化，否则保留绝对概率：

```python
if len(all_buckets) >= 2 and 0.90 <= total_prob <= 1.10:
    normalized_probs = [p / total_prob for p in raw_probs]
else:
    normalized_probs = list(raw_probs)
```

`0.90 / 1.10` 上下界用于排除「只抓到部分桶」的情况（部分覆盖时归一化同样会系统性放大）。

### 交易员表「平均 ROI」极端值 —— 已查证：**不是真实数据**，已修（提交 `fix(discovery)`）

用户看到的 `+19781081.2%`（SusanWarrenHR）与 `+795366.7%`（norealtime）不是真实收益，是**统计口径缺陷**。三层证据：

**证据一：代码根因**
`services/wallet_discovery.py` 的 `avg_roi` 原本是**算术平均**：

```python
avg_roi = sum(market_rois) / len(market_rois)      # 各市场 ROI 直接平均
其中 m_roi = (sell_revenue - buy_cost) / buy_cost * 100
```

只要某个市场的 `buy_cost` 是几分钱（预测市场低价建仓很常见），`m_roi` 单点就能冲到 `1e9%` 量级，**一个市场就把整个钱包的"平均"拉到不可解释的数**。同一段代码的 fallback 分支本来就写着加权公式 `total_pnl / total_invested * 100`，说明**设计意图是加权，主分支走偏了**，不是新功能。

**证据二：实测数值不自洽**
`debased` 钱包接口原值 `avg_roi = 92,258,575,450%`（922 亿%）。重算后同一钱包：

| 口径 | 值 |
|---|---|
| 旧（算术平均） | **922 亿 %** |
| 新（总盈亏 / 总投入） | **6,692%** |
| 实际投入成本 | $1,202,058 |
| 实际盈亏 | $80,445,624 |

`80,445,624 / 1,202,058 = 66.92` → 6692%，**分子分母对得上**。而 922 亿% **没有任何分母能支撑**——这就是伪值的判据。

**证据三：伴随指标同样失真**
同一行 `wins=150, losses=0, win_rate=1.0, max_drawdown=0.0`：149 个市场**零亏损、零回撤、100% 胜率**。真实交易数据不会出现这种组合。
