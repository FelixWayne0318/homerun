# 执行层改造方案（对照 polymarket-copy-trading-bot）

时间：2026-11-18（Asia/Shanghai）
对象：Homerun 本地 Polymarket 单平台，`traders_copy_trade` 实盘链路

## 一、现状核对（基于当前代码，不是推测）

| 参考仓库的做法 | Homerun 现状 | 结论 |
|---|---|---|
| BUY 按股数下单，避免 USDC 预算超买 | `order_manager` 已是 `shares = notional / price`，并有 `_MIN_LIVE_SHARES` 下限 | 已满足，不需改 |
| BUY 用 FOK，SELL 用 FAK | 实盘 `time_in_force` 取 leg，缺省 `GTC` | 有差距，可配置化 |
| 发送前落 pending（at-most-once） | `place_order` 有 metadata 幂等键、`_persist_orders`、`_validate_and_reserve_order` | 骨架已有 |
| 回包三分：成交 / 拒绝 / 未知 | 未知一律 `FAILED` 且释放额度 | **真实缺陷，已修** |
| 未决单占额度，交对账 | 有 `fast_idempotency`、`_sync_provider_open_orders`、reconciliation worker | 机制可用，缺“未知单”入口 |
| 深度为累计档位、价格带 0.05–0.95 | `min_live_liquidity_usd=150`、`max_entry_price=0.98`，档位累计逻辑部分具备 | P1，本轮不动 |

关键发现：代码在传输层已经明确“FAK/IOC 的 BUY 超时后不重试，避免重复链上单”，但异常路径仍把订单记 `FAILED` 并释放额度。这意味着一旦交易所实际成交，本地会认为失败、额度被释放，下一个信号可以在同一方向再开一笔，形成事实上的重复敞口。

## 二、方案与优先级

### P0-1 未知结果不再当失败（已执行）
- 在 `place_order` 中增加 `submit_attempted`：仅在签名订单真正递交给 CLOB 前置为 True。
- 该标志为 True 且方向为 BUY、且非鉴权失败时，异常路径改为：
  - `OrderStatus.PENDING`
  - `error_message = unknown_submit_outcome: ...`
  - **保留额度不释放**
- 鉴权失败、未递交（同步 transport / 前置闸门失败）仍按 `FAILED` 释放，保持原语义。
- 验收：`pytest -k "live_execution or place_order"` 25 项通过；`pytest -k "order_manager or orchestrator"` 257 项通过。

### P0-2 BUY 的 FOK 必须是股数口径（已执行 + 已配置）
- 原实现：FOK/FAK 走 `MarketOrderArgs`，BUY 时 `amount = price × size`（SDK 按 USDC 解释）。成交价优于限价时会多买股，正是参考仓库点名的问题。
- 修改：BUY 的 FOK/FAK 改走 `OrderArgs(price, size)` + `postOrder(FOK)`；SELL 仍用 `MarketOrderArgs(amount=shares)`，因为 SELL 的 `amount` 本来就是股数。
- 配置：仅对「跟单实盘微仓1」加 `live_time_in_force=FOK`，`mode=live` 才生效，影子模拟与其它策略的 leg 不受影响。
- 验收：`place_order` 语法检查通过；25 项单测通过；影子 26 笔 / 20 持仓未变；实盘微仓 0 单 0 仓、仍 paused。

### P1 收紧口径（第二轮已执行）
1. **深度改为累计档位**：`order_manager` 新增 `_cumulative_ask_depth_usd`，按 `max_execution_price` 价格带内所有卖档累计 `price×size`；低于 `min_live_depth_usd` 直接 skip，拒绝原因 `min_live_depth`。该闸门**默认关闭**（默认 0），只有显式配置的机器人启用，避免误伤加密等薄盘策略；实盘微仓配置为 50。原来的 `min_live_liquidity_usd` 用的是市场级 `liquidity_usd` 标量，口径不对，保留但不再作为实盘深度的依据。
2. **价格带上限 0.95**：实盘微仓 `max_entry_price` 0.98 → 0.95（配置层，不改代码）。
3. **SELL 用 FAK**：`exit_executor` 的默认 TIF 从 `GTC` 改为 SELL 时 `FAK`，退出不再挂单等对手盘；增量提交走 `MarketOrderArgs(amount=shares)`，部分成交按股数精确入账。
4. **未知单闭环**：`success=false` 的 `killed/timeout/unknown` 回复也进 `PENDING`（原来直接 `FAILED` 释放额度）。反查按订单家族分两条路径：GTC 用 `get_open_orders` 按 metadata 认领挂单（挂单不会出现在成交记录里），FOK/FAK 用 `get_trades` 按 `asset_id + after` 反查成交；每次反查先查挂单再查成交，命中即落 `OPEN`/`FILLED`/`PARTIALLY_FILLED`。只有在“对应视图确实读到、且两者都没有”时才释放额度；视图读不到则保持 `PENDING` 并标 `unknown_buy_unverified_needs_manual` 交人工，不做猜测。

### P2 选人过滤（不做）
参考仓库的信号层（PMWallets 托管、胜率置信区间下界、剔除单一最佳市场）属于选人质量，和本地钱包池逻辑不同源，迁移成本高、收益不确定。本轮明确不动。

## 六、已知限制（不隐藏）

- 成交反查按 `asset_id + 时间窗 + side + 价格 ≤ 限价` 匹配，不按订单号。当前只有 1 个实盘机器人，误匹配概率可忽略；同日多机器人同标的买入时需要改为按 `taker_order_id` 精确匹配。
- 深度闸门使用 WS 盘口快照：机器人显式配置了 `min_live_depth_usd` 但快照缺失时**直接拒绝**（`min_live_depth_unavailable`），不再静默放行。
- 未知单反查任务在进程重启后由 `_restore_runtime_state` 自动恢复（24 小时内、`unknown_submit_outcome` 状态行），超过 24 小时的保持人工处理。
- 退出重投最多 3 次、每次只降 1 分；深度极差的盘口会在 3 次后停在 `failed`，需要人工处理，不会无限降价贱卖。
- GTC 未知单若没有 metadata（历史 leg 或非 fast 路径），无法在挂单视图里认领，会长期占额度并标人工。

## 七、与当前系统的融合核验

| 融合点 | 结论 | 证据 |
|---|---|---|
| 状态机 | `PENDING` 经 `live_execution_adapter._map_trading_status` 映射为 `submitted`，不是 `failed`，session_engine 不会把它当失败后重投新单 | 代码核对，未知单不会造成重复建仓 |
| 盘口数据 | 实盘路径提交前先解析 `live_book_payload`，深度闸门与 `max_spread_bps` 闸门用的是同一份快照，不存在“闸门拿不到盘口”的空转 | `order_manager` 1400–1460 行 |
| 退出重投 | FAK 无对手盘会立即失败，而梯子只重投 `planned` 子单；已补“失败后按 1 分降价重投、最多 3 次” | 本地注入实验：修复前第二遍 `submitted=0`，修复后连续 3 次重投后终止 |
| 影子隔离 | 所有改动都在 `mode_key=="live"` 分支或实盘专属方法内 | 影子仍 26 笔 / 20 持仓 |
| 未知单无 metadata | 重启后按 `asset_id + side + price + size` 唯一匹配认领挂单；多于一个候选则保持 `PENDING` 交人工，不释放额度 | 7 场景矩阵两轮复验一致 |
| 跨重启恢复 | 启动时自动恢复 24 小时内的未决 BUY 反查，不再依赖进程存活 | `_restore_runtime_state` |
| 深度闸门 fail-closed | 配置了深度下限但盘口读不到时拒绝下单，闸门不会在关键时刻空转 | 代码路径 |
