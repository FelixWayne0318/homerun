## 0. 一句话结论

系统不是坏了，是**后端完整、前端半成品、产品引导缺失、账本口径不一致**。
后端接口封装 52 个，组件层实际引用 25 个（接线率 48%）；沙盒账户模块 9 个接口里 5 个没有 UI 入口。
默认配置下（无 trader、kill switch 开着）影子交易一定零成交——这不是故障，是缺引导。

先读上游自带的 `docs/plane_isolation_handoff.md`，里面写明 "Do not push to origin until the operator has tested. All commits local-only"，说明上游自己也处于半成品阶段。

## 1. 阻断项（不修则业务闭环不成立）

### B-1 交易平面无进程守护，重启即失效
- 现状：`~/Library/LaunchAgents/com.homerun.worker-trading.plist` 已存在且 `plutil -lint` 通过，但
  `launchctl bootstrap gui/$(id -u) <plist>` 稳定返回 `5: Input/output error`
- 当前进程是 `nohup` 手动拉起（PID 44396，PPID 非 launchd），**机器重启后交易平面消失**
- 影响：`trader_orchestrator` 随之停摆，页面长期停在"启动中..."
- 建议：核对 plist 与 `com.homerun.worker-detection.plist` 的差异；若 launchd 仍拒绝，改用 `RunAtLoad` 的
  `launchd` 替代方案（`LaunchDaemon` 或在 `backend` 启动脚本里 fork 平面），并纳入部署文档

### B-2 Python 3.11 下 dataclass 可变默认值
- 位置：`backend/services/trader_cycle_context.py:208`
- 原代码：`acquire_timings_ms: Mapping[str, int] = MappingProxyType({})`
- 现象：`import` 阶段即 `ValueError: mutable default <class 'mappingproxy'> ... use default_factory`，
  trading 平面启动直接崩（`host.py:1306` → `trader_orchestrator_worker.py:118` → 该文件 168 行）
- 已做临时修改：改为 `field(default_factory=lambda: MappingProxyType({}))`，**未提交**
- 补充：对全仓做了 AST 扫描，**同类隐患仅此一处**，其余 dataclass 无可变默认值

### B-3 没有交易员，编排器空转
- 证据：`GET /api/traders` → `{"traders":[]}`；
  `backend/workers/trader_orchestrator_worker.py:9721` `for trader in cycle_traders:` —— 空列表循环 0 次
- 现象：`signals=0 decisions=0 orders=0`，沙盒账户零成交
- 性质：产品缺引导（无种子交易员、无首次创建流程），不是 bug
- 建议：提供最小引导——机器人页空态给出"创建第一个机器人"的明确下一步，并在文档写清
  "启用策略 ≠ 产生交易，交易单位是 trader"

### B-4 前端没有"手动模拟下单"入口
- 后端：`backend/api/routes_simulation.py:308` `POST /accounts/{account_id}/execute`
- 前端封装：`frontend/src/services/apiCore.ts:899 executeOpportunity`
- 组件层调用数：**0**（`grep -rn executeOpportunity --include=*.tsx` 无命中）
- 影响：想在沙盒里手动买一笔，只能走 `/docs` 或 curl

## 3. 账本一致性缺陷（本次实测暴露）

实测：对机会 `settlement_lag_6221478_6221480_1d8eaf72_1794057243` 执行 2 次 `POST /execute`，
`position_size=10`。接口返回 `status=open`、`total_cost=7.58775`、`slippage=0.03775`、`expected_profit=2.22735`。

成交后账户读数：

| 字段 | 值 | 问题 |
|---|---|---|
| `current_capital` | 9984.8245 | 较 10000 减少 15.1755（两笔含滑点成本）——正确 |
| `book_value` / `market_value` | 15.1 / 15.1 | 比实际支出少 0.0755，即**滑点未计入持仓成本**；且 two 值相等说明**市值未按现价重估** |
| `total_pnl` / `unrealized_pnl` | 0.0 / 0.0 | 与上一行矛盾：成本口径已差 0.0755 |
| `roi_percent` | -0.151755% | 由资金减少推出，却与 `total_pnl=0` 并存——**两个指标口径不一致** |
| `equity-history` 第二条 | equity=10000.0 | 成交后净值仍记 10000，**未反映 9984.82** |
| `open_positions` / `total_trades` | 4 / 2 | 一笔 NegRisk 机会 = 2 条腿 × 2 笔，符合预期 |

建议：统一账本口径（滑点是否入成本、市值多久重估一次、PnL 与 ROI 是否同源、净值快照的触发时点），
并补一条对账断言（`current_capital + market_value == initial_capital + total_pnl`）。

## 4. 文档与实现不一致

- `README.md:63`：`Every strategy is a DB-managed Python class. Edit in the UI, validate, backtest, enable — hot-reloaded in seconds.`
- 实际：策略 `enabled` 只控制热加载；下单单位是 `trader`（`trader_orchestrator_worker.py:9721`），
  且必须满足 `source_configs` 恰好 1 条
- 结果：用户"启用 30 个策略"后仍零成交，误判为系统故障
- 建议：README 补一句"策略启用 ≠ 交易；需创建 trader 并绑定策略/来源"
