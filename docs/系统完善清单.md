### 2.1 回测采样密度未接线（本次回测实测暴露，已交叉验证）

`POST /api/backtest/runs/enqueue` 接受 `discovery_sample_interval_seconds`（默认 **1800 秒**）与
`discovery_max_ticks`（默认 **96**），后端一路透传：
`routes_backtest.py:103-104,181-182` → `unified_runner.py:1105-1209` → `strategy_backtester.py:4658-4664`。
但 `BacktestStudio.tsx` 里这两个字段**一次都没有出现**，所以任何回测都只能跑 30 分钟一采样的默认值。

实测后果：47 分钟窗口 → `int(measured_seconds / 1800) = int(1.59) = 1` → 整段只采 **1 个 tick**。日志原文：

```
replay_discover: bus replay binned 1010 events across 1 ticks
```

1010 条 bus 事件全部挤进同一格，crypto 策略只剩一个时间点做决策，于是 `0 synthetic opps`
→ 引擎退回读 `live opp_history`（该窗口无记录）→ **0 信号 → 0 单**。这解释了本轮回测
`completed / trades=0 / return=0.0%` 的直接原因。

> **必须澄清的一点（避免后续重复劳动）**：引擎**已经支持** crypto 策略的 `on_event` 派发，
> 不存在"crypto 策略族不能回测"这个问题。实测：`_replay_event_kind_for_strategy` 对
> `subscriptions=["crypto_update"]` 返回 `crypto_update`，`_has_custom_on_event(strategy)` 为真，
> `dispatch_via_on_event=True`；配套单测 `tests/test_backtest_crypto_on_event_dispatch.py`
> **13 条全部通过**（6.72s）。真正的缺口只有采样密度。不要再去"补 on_event 支持"。

修法（属补完，不是新功能）：Backtest Studio 的 Setup 增加两个输入——采样间隔秒数、最大 tick 数；
crypto（5m/15m）策略建议 2–5 秒间隔 + `max_ticks` 上限 10 万～30 万，或按 `strategy.timeframe` 自动取默认。
注意此修与第 5 节的"回测 OOM"是两个独立问题：内存爆在**全量载入快照/价格网格**，
采样密度影响的是 `on_event` 调用次数，不要混为一谈。

## 3. 账本一致性缺陷（本次实测暴露）

实测：对机会 `settlement_lag_6221478_6221480_1d8eaf72_1794057243` 执行 2 次 `POST /execute`，
`position_size=10`。接口返回 `status=open`、`total_cost=7.58775`、`slippage=0.03775`、`expected_profit=2.22735`。

成交后账户读数：

| 字段 | 值 | 问题 |
|---|---|---|
| `current_capital` | 9984.8245 | 较 10000 减少 15.1755（两笔含滑点成本）——正确 |
| `book_value` / `market_value` | 15.1 / 15.1 | 比实际支出少 0.0755，即**滑点未计入持仓成本**；且 two 值相等说明**市值未按现价重估** |
| `total_pnl` / `unrealized_pnl` | 0.0 / 0.0 | 与上一行矛盾：成本口径已差 0.0755 |
| `roi_percent` | -0.151755% | 由资金减少推出，却与 `total_pnl=0` 并存——**两个指标口径不一致** |
| `equity-history` 第二条 | equity=10000.0 | 成交后净值仍记 10000，**未反映 9984.82** |
| `open_positions` / `total_trades` | 4 / 2 | 一笔 NegRisk 机会 = 2 条腿 × 2 笔，符合预期 |

建议：统一账本口径（滑点是否入成本、市值多久重估一次、PnL 与 ROI 是否同源、净值快照的触发时点），
并补一条对账断言（`current_capital + market_value == initial_capital + total_pnl`）。

### 6.5.5 机器人状态把"急停阻断"与"引擎停止"分开（已修，`bfa3eac7`）

现象：全局急停开着时（`kill_switch=true` → `runtime_state.state=blocked`），详情页每个机器人徽章都显示
`Engine Stopped`，看起来像"这个机器人启动失败"，实际前端只判了一个条件（`TradingPanel.tsx:7490`）：

```js
const orchestratorRunning = orchestratorStateKey === 'running'
```

`blocked ≠ running`，于是所有机器人被一律判成"引擎停止"。

改法：`resolveTraderStatusPresentation` 增加第三个参数 `orchestratorBlocked`，在
`!orchestratorExecutionActive` 分支内优先返回新状态 `engine_blocked`（红色徽章 `Engine Blocked`），
否则维持原 `engine_stopped`。三处调用（侧栏 roster、详情页徽章、排行榜圆点）同步传入；
`botRosterPanel.statusEngineBlocked` 补进 9 个语言包（中文"急停阻断"），分组顺序插在 running 之后。

边界说明：机器人自身 `is_paused` 的判定仍排在前面——机器人自己停了显示 `Bot Stopped`，
比"被急停挡住"更具体，这一优先级未改动。

验证：急停开启状态下详情页徽章显示红色 `Engine Blocked`（截图留证）；页面含中文"急停阻断"
且不出现原始 key 文本；`npx tsc --noEmit` 仍 13 条（`TradingPanel` 9 + `AIChatView` 4），
与基线完全一致。反向场景（`blocked=false` 时回落到 `Engine Stopped`）沿用未改动的原分支，
未单独造数据实测。
